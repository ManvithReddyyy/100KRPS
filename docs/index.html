personal project / backend systems

hey, i'm manvith. i built 100KRPS to understand how to optimize backend systems for real traffic, failures, slow users, and growing data.

100KRPS is a real-time gps backend built with go, redis, and postgresql. it accepts a driver's location update, publishes the newest position to live viewers, and saves the location history in the background.

this page is for reading and learning. i want to explain everything i know from building the project: what each main part does, what data it handles, how it behaves under pressure, and where its own limits are.

01 / the problem

why not just insert every ping?

because that is what everyone does on the first try, and it works right until it does not.

at low traffic, a ping hits postgres and everyone goes home happy. at high traffic, every ping starts fighting for database connections, disk writes, wal work, and attention. the live location update should not be standing in the same queue as historical storage.

so 100KRPS splits the job: show the newest position fast, then save the full history in the background. two jobs, two paths, fewer bottlenecks.

02 / the whole request path

follow one ping for a minute

picture a trip being created. the trip metadata and owner token are stored in redis, the driver sends a coordinate, and the live map waits for the next update.

solid line = work that happens during a ping moving square = one update on its way
a rough sketch of where the work goes

The same ping has two jobs: update what people see now and build the history that can be queried later.

  1. go checks the request.

    the server applies limits and middleware, then the handler validates the payload and token. no drama, no extra database lookups.

  2. redis runs the whole hot path once.

    one lua script checks the trip, verifies the token hash, updates the location, runs haversine geofence math, and changes the trip status if the driver arrived.

  3. the ping gets sent two ways.

    one copy goes to live viewers through pub/sub. one copy gets appended to a redis stream for history. postgres is not sitting on the ping's hot path.

  4. the map receives just the latest useful frame.

    each go node keeps bounded channels for viewers. if someone's map falls behind, stale frames get dropped instead of blocking everyone else.

  5. a background worker saves the history.

    it reads up to 1,000 pings or waits 250 ms, bulk copies the batch, then acknowledges the stream. less tiny sql work, more organized disk work.

03 / why these pieces

meet the team

go

go handles the HTTP path, validation, metrics, and live connections. the standard library keeps the request route easy to inspect instead of hiding it behind a big framework.

redis

redis holds the hot trip state, runs the lua transition, publishes live frames, and buffers ping history. it is the fast lane, not a magic "nothing ever fails" box.

postgresql

postgres stores trips and the long-term ping history. bulk copy does less tiny sql work and time partitioning can keep old history from becoming one gigantic table.

server-sent events

sse keeps a browser connected so location frames arrive as they happen. the map does not need to hammer the server with "anything new yet?" requests.

redis streams

the stream separates "accept this ping" from "save this ping forever." consumer state remembers pending messages, and stale pending work can be claimed again.

metrics and load tests

atomic counters track requests and latency. k6 creates the traffic and checks the answers, so changes can be compared instead of just vibe-checked.

Demo status: this is a static project page, not a running backend. Redis and PostgreSQL are required when the API is started locally. An interactive hosted demo would deploy the API and both services together.

one core, 12,000 requests

the main unit of scale in 100KRPS is a cpu core. the target is simple: about 12,000 requests per second per core. this is measured on a complete ping flow, with redis and the rest of the setup capable of keeping up.

a request is not pure cpu the whole time. it waits on sockets, redis round trips, memory, scheduling, locks, parsing, and system calls. the 12k number means the cpu and the whole little pipeline are balanced enough that one core can finish about 12k complete request flows each second.

i love how cores function

an 8-core server has 8 places that can run work at the same time. go does not stick one request to one core forever; it schedules thousands of goroutines across the available processors while queues and caches change around.

so the rough math is 8 x 12,000 = 96,000 rps. that is why the project calls the goal roughly 100k rps. it is the 12k-per-core target multiplied across 8 cores, not a random number pulled out of the cloud.

what happens inside one request

  1. the network is ready.

    the operating system accepts a connection and passes the http request to the server. cpu, interrupts, memory copies, and socket queues participate before application code begins.

  2. go performs the local work.

    middleware assigns request metadata, checks limits, parses the small payload, validates values, and prepares the redis command. short, predictable work helps every core stay available for more requests.

  3. redis performs the atomic operation.

    the ping script updates live state and appends history work in one event-loop operation. redis time is not free cpu time: network latency and redis scheduling still affect how quickly go receives the result.

  4. the response leaves the node.

    the server serializes a small response and writes it to the socket. throughput at the end of the pipeline is limited by the slowest shared resource, not just the fastest request handler.

how cores scale

perfect scaling would mean 8 cores give exactly 8 times 1 core. real life has redis limits, socket limits, memory bandwidth, cache misses, connection churn, lock contention, interrupts, network cards, and load-balancer work. some of those do not scale just because the cpu count went up.

that is why 12k per core is a benchmark result, not a promise. as traffic rises, we watch throughput, p50/p95/p99 latency, interrupted iterations, cpu use, and errors. the test is only real if the load generator can sustain it too.

why cores become the bottleneck

a core becomes saturated when it has no breathing room—runnable work stacks up or contention keeps everything waiting. average cpu can look fine until queueing time spikes in the tail.

allocation pressure, mutexes, logging, redis round trips, and network work can all stop the 12k-per-core result from showing up. more cores do not fix a redis event-loop limit, disk i/o limit, or network bandwidth limit. the slowest shared piece wins.

why this target is useful

the per-core target gives a clean capacity estimate. 4 cores suggest 48k rps, 8 cores suggest 96k rps, and 16 cores suggest 192k rps—but only if redis, networking, disk, and the load generator can carry the extra work.

the whole benchmark is the point: cpu model, core count, machine, duration, target ramp, data path, result, latency, and interruptions should all travel together. otherwise a huge rps number is just a number.

04 / why this helps under load

what happens when stuff gets weird?

redis alone does not make a system crash-proof. the real trick is using queues, bounded buffers, acknowledgments, and recovery paths so one slow piece does not ruin every other piece.

  1. Traffic spikes should not become database spikes.

    With a synchronous INSERT for every ping, a request burst becomes a database burst. Redis first updates the latest state and appends a stream event. The API returns without waiting for PostgreSQL, giving the database time to process fewer, larger writes.

  2. A temporary database slowdown becomes a buffer, not a crash.

    The worker reads up to 1,000 stream entries and flushes at least every 250 ms with CopyFrom. This absorbs a gap between incoming traffic and database throughput. The buffer is not infinite: the stream is capped near one million entries, so backlog and drain speed need monitoring.

  3. A dead flusher should not lose pending work.

    The worker acknowledges stream messages only after a database write succeeds. If a consumer dies before acknowledging, another worker uses XAUTOCLAIM to pick up entries idle beyond the configured threshold. This provides at-least-once processing, not exactly-once delivery.

  4. A slow viewer should not slow down ingestion.

    Each local SSE viewer gets a bounded channel with 16 slots. If the buffer fills, stale coordinates are dropped instead of blocking Redis message handling or creating an unbounded memory queue. On a live map, the newest position matters more than replaying old frames.

  5. An HTTP handler panic can be isolated to one request.

    Recovery middleware logs the panic and returns HTTP 500 instead of dropping the request socket. It contains handler errors, but not process, machine, Redis, or database failures.

  6. More API traffic can spread across API replicas.

    Trip state lives in shared Redis instead of only one Go process, allowing several API nodes to serve requests behind a load balancer. Redis and the stream worker must handle the additional shared load, and PostgreSQL must keep draining the stream.

These choices handle more traffic by reducing per-ping database work, batching writes, and supporting API replicas. They manage more historical data by batching inserts and preparing the ping table for time-based partitions. The current migration still routes data to a default partition, so date-specific partitions must be created and maintained. Backlog depth also needs to stay visible so PostgreSQL can keep up.

There are still failure limits: a Redis outage makes the ping hot path unavailable; a PostgreSQL outage can allow the bounded stream to age out old entries. A real deployment needs health checks, alerts, durable Redis settings, capacity tests, backups, and a recovery plan.

Durability note: Redis holds live state, runs the atomic ping operation, sends Pub/Sub events, and owns the stream queue. Redis-in-memory storage does not automatically mean durable storage. The sample Compose setup disables Redis persistence, and the Lua script caps the stream near one million entries. Production settings would need matching persistence, replication, retention, and backup goals.

07 / the motivation

why build this instead of another crud app?

honestly, i just love backend systems.

the queueing, the trade-offs, the tiny decisions that turn into big latency spikes. yeah, that stuff is my kind of interesting.

i built this because reading architecture diagrams only gets you so far. i wanted to watch the system get faster, break, back up, recover, and teach me something in the process.

gps data gave me a fun excuse to learn about redis, concurrency, batching, cpu cores, recovery, and throughput without making it just another to-do app.

the goal isn't to say every backend is simple. the goal is to understand why each piece behaves the way it does under pressure.

now i want to take those lessons into better systems, bigger experiments, and my next build. if backend engineering is your thing too, this one's for you.
